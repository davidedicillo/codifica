# Independent backend review

Reviewed `IMPLEMENTATION.md`, `next/server/`, `next/tests/`, and the API owner's `next/api-report.md`. This is a read-only implementation review except for this report. The existing 25-test suite was inspected, not rerun; its passing result is the implementer's reported evidence. One additional isolated HTTP reproduction was run against a temporary SQLite database.

## Resolved finding

**P2 — Reject an empty root message ID before inserting a message.** `next/server/messages.py:81-82` checks `if payload.rootMessageId`, while `next/server/schemas.py` accepts an empty string for that field. An authenticated `POST /api/v1/channels/{channel}/messages` with `{"body":"hello","rootMessageId":"","requestId":"<valid UUID>"}` bypasses `root_exists` and reaches the insertion at `messages.py:99-104`. SQLite rejects the empty foreign key, producing **500 `Internal Server Error`** rather than the contract's structured 400 `INVALID_ARGUMENT`. Reproduced with `raise_server_exceptions=False`; a subsequent history read confirmed zero messages, so rollback is intact. Reject empty strings in the schema or validate any non-null root ID; cover this with a targeted regression test. The equivalent empty history filter also bypasses root validation and silently returns no results, so align that validation if the field is intended to always identify a real root.

**Resolution reviewed at `feec9d77b9a73659ba512e7bb2b30bed8a15511f`:** `next/server/schemas.py:49` now constrains non-null POST `rootMessageId` values with `min_length=1`; `next/server/messages.py:45` applies the same constraint to the GET query parameter. Empty values therefore fail request validation before reaching route/database logic, while omitted/null root IDs retain the root-message behavior. `next/tests/test_messages.py:39-43` asserts 400 for both malformed POST and GET requests. The existing application validation handler supplies the structured `INVALID_ARGUMENT` error. The API owner reports **26 passing tests** after the fix; this follow-up verified the committed implementation and assertions without rerunning the suite. The finding is resolved.

## Contract and security assessment

- Persistent identity is keyed by issuer/subject, with verified-email admission and target-email validation at human join. Authlib owns the OIDC exchange/ID-token validation; the application explicitly requires verified email, issuer, and subject (`identity.py:227-269`). Tests exercise the adapter boundary using a provider double. A real provider deployment remains unverified, as correctly disclosed in the API report.
- Browser administration requires a human session; mutation authentication checks the exact configured Origin and CSRF token. Bearer principals are channel-scoped agents and cannot invoke human administration. Session, invitation, and agent credentials are hashed in storage. Registration recovery uses keyed deterministic credentials and validates the original payload/request ID and active membership before returning the credential.
- Ownership checks, membership scoping, human removal cascading to linked agents, archival write rejection, invitation expiry/revocation, and full-history access match the updated contract. No concrete authorization bypass was found in the reviewed paths.
- Activity ACK transitions operate in one transaction and distinguish the outstanding batch, immediately preceding ACK, and obsolete ACK. Persisted batch responses provide stable retry payloads. Held polls reserve the participant before awaiting, reauthenticate on each acquisition, do not hold a database connection during waits, and release reservations on cancellation (`activity.py:12-109`). This matches the documented single-worker restriction; multi-worker support is not claimed.
- Messages, delivery routing, event sequence allocation, pinned document references, and mutation replay are committed together. Document edits check expected revision under `BEGIN IMMEDIATE`, with immutable revision rows and transactionally resolved citations. The reviewed tests include competing connections, retry idempotency, cross-channel reference rejection, restart and backup restore.
- Tests cover the main acceptance paths with meaningful observable assertions, including held-poll revocation/cancellation and bootstrap history that does not create inbox work. They do not prove live OIDC configuration, TLS/proxy behavior, or the actual 50-second network acceptance run; these are correctly left to deployment/integration verification.

## Verdict

The backend substantially satisfies the updated local implementation contract. The reproduced malformed-root validation issue is resolved in the reviewed commit, and no actionable findings remain from this pass. This is not a production deployment approval or an exhaustive security audit; the integration and deployment verification boundaries above still apply.
